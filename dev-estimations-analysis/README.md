## О проекте

Каждая команда разработки живёт с одним вопросом: *насколько можно верить оценке, которую дал разработчик?* Обычно на него отвечают анекдотами («умножай на два») или коэффициентами, взятыми с потолка.

Здесь на него отвечают данные — **80 709 задач из трёх независимых публичных датасетов**, в которых для каждой задачи записаны и оценка, и фактические трудозатраты.

## Ключевые находки

| | |
|---|---|
| 🎭 | **34 % «идеально точных» оценок — учётный артефакт, а не точность.** Доля падает с 60 % на часовых задачах до 0.8 % на многодневных: это списание времени по плану вместо измерения. Без изоляции этих строк все метрики врут. |
| 📉 | **Смещение меняет знак с размером задачи:** мелкие недооценены (×1.22), крупные переоценены (×0.37). Фольклор «умножай на два» ошибается направлением для половины бэклога. |
| 🔁 | **Эффект воспроизводится на всех трёх датасетах** — разные индустрии, культуры, единицы измерения (часы, минуты, помидоры). Наклоны −0.24 / −0.17 / −0.81, все p < 1e−140. |
| 🙅 | **Личность исполнителя объясняет 3 % дисперсии**, размер задачи — 9 %, все факторы вместе — менее 15 %. Персональные коэффициенты оценщика — шум, выданный за сигнал. |
| 🗣 | **Коммуникационная работа не попадает в оценки:** планёрки ×2.38, статусные встречи ×1.52, обучение ×1.46 — при том что баги и доработки оцениваются с запасом (×0.75–0.82). |
| 🤖 | **ML улучшает не медиану, а хвост:** −7.3 % RMSE в логарифмах, устойчиво на пяти временных окнах. Модель отвечает на вопрос «какая задача уедет в разы?», а не «сколько точно займёт эта». |
| 📏 | **Правильный продукт — интервал, а не число.** Conformal-калибровка (CQR) поднимает покрытие с 68 % до 80.5 %. |

## Методология вкратце

* **Всё в логарифмах.** `факт/оценка` — положительная скошенная величина; в логах ошибки «×2 дольше» и «×2 быстрее» симметричны, а `exp(MAE_log)` читается как «типичная ошибка в N раз».
* **Дедупликация.** В SiP 12 299 строк, но 10 266 задач: многолюдные задачи дублируются с теми же тоталами. Без этого крупные задачи получают вес ×2–×5.
* **Точные совпадения изолированы.** Каждый результат считается дважды — на полных данных и на честной подвыборке.
* **Только временное разбиение.** Случайный `train_test_split` — утечка: задачи одного спринта коррелированы.
* **Никаких post-hoc признаков.** `TaskPerformance` и `DeveloperHoursActual` — функции от таргета, исключены.
* **Rolling-origin валидация** на 5 окнах вместо одного сплита.
* **Conformal prediction** для интервалов с проверкой эмпирического покрытия.

## Данные

[Derek-Jones/Software-estimation-datasets](https://github.com/Derek-Jones/Software-estimation-datasets) — коллекция публичных датасетов оценки трудозатрат, где для каждой задачи известен и план, и факт. Использованы **SiP** (10 266 задач), **CESAW** (60 284) и **Renzo Pomodoro** (10 159). Данные не хранятся в этом репозитории, а скачиваются при запуске.

Источники: [SiP](https://arxiv.org/abs/1901.01621) · [CESAW](https://arxiv.org/abs/2106.03679) · [Renzo Pomodoro](https://shape-of-code.com/2019/12/15/the-renzo-pomodoro-dataset/)
